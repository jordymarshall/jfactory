# jfactory

**Done means right.** A change is done only when it is right: it serves the outcomes in `outcomes/README.md` and crosses none of its non-goals, keeps every standing goal of the jobs it touches (`outcomes/<job>.md`), meets the standards map (`.jfactory/standards.md`) and meets its own criteria, each proven at the current commit. Green CI, passing tests, an approved review or a completed checklist is evidence toward done, never done by itself. Done but not right is not done: keep working, or report it as not done.

Work proactively inside the user's objective. This is a portable engineering workflow built around selected, pinned Lauren Tan pstack skills. Read [host compatibility](references/compatibility.md) before using upstream methods. Repository decisions and current user authorization govern scope. Do not import another project's customer assumptions, architecture, credentials or release permissions.

For a plain explanation of the feedback paths and owner checkpoints, use [how the loops work together](references/methodology.md).

## Set up the repository once, reconcile when needed

Treat "Setup jfactory" as the full [repository adoption procedure](references/setup.md), including document reconciliation, product alignment, executable tools, environment setup and delivery gates. Continue after installation without requiring another prompt. Reuse canonical documents, preserve unique decisions, and reconcile stale or conflicting project-owned guidance in the adoption diff. Setup always interviews the owner about the product, even when the code suggests the answers, and records the answers in the setup record. It is not finished until `scripts/setup_check.py --remote` passes, or reports only areas blocked on a named owner step. Re-running setup, including after an update, resumes the same record, reruns the checker and repairs what it reports. Report readiness per capability with evidence and exact gaps. On a blank project, architecture is proposed and capabilities are unimplemented until built.

Before each substantial feature, review the customer hypothesis and intended experience in depth, reusing settled answers and clarifying unresolved choices before dependent implementation. Use an existing product/grilling skill if available; otherwise ask focused questions with recommendations. jfactory does not mandate a whole-product interview for every bug or replace the owner's product process.

## Establish and resume an objective

Every request that changes behavior starts from an objective. Route it through the loops it needs using the [routing table](references/methodology.md#route-each-request-through-the-right-loops), record the route and reason in the objective, and change the route when the signals there appear. Write it with the [objective contract](references/verification.md#objective-contract) ([template](templates/objective.md)) in the task location the setup record names, usually the GitHub issue for the work. For a small fix, a few lines in the PR are enough. Record the useful outcome, owner decisions versus agent assumptions, scope and non-goals, observable acceptance criteria with the evidence each needs, and the next review point. Ask the owner only about consequential choices that are still open; propose an answer with each question. State the objective and how it will be checked before substantial implementation. On continuation, read that record and relevant code/evidence; do not require the user to repeat it. If the objective is complete, propose the next one rather than silently expanding scope.

At the start of repository work, identify the loaded jfactory path and installed source revision when available. For concurrent workspaces or overlapping PRs, follow [worktree coordination](references/worktrees.md). Instructions and evidence in another checkout are not automatically current here.

For a change to screens users see, the verifier uses each changed journey step by step, looking at the screen after every action and noting what it sees (jfactory-ux `study.py step`), and reviews the screenshots against the standards. Verifiers judge whether a change is right, not only whether its checks pass, against the project's own sources of truth as well as its tests: `outcomes/README.md` (the customer, the outcomes that matter and the non-goals), the standards map (`.jfactory/standards.md`), and each job-to-be-done document in `outcomes/`, which says what the user is trying to do and how every standing goal is proven. A work item's objective names the job goals it adds, changes or relies on, and its PR says why it is right: what could make it wrong even though every check passes, and how that was ruled out. A weekly method audit checks the checkers across merged PRs ([check the checkers](references/methodology.md#check-the-checkers)). When a document and the product disagree, decide which is wrong: update an out-of-date document in the same change, or report the product defect; never edit a document to match broken behavior. Use the [verification contract](references/verification.md) to map every criterion to required evidence scopes, including `judgment` for qualities such as clarity that need a rubric rather than a test, and `scripts/verify_plan.py plan` to derive affected features and CI suites from the changed files. Before a change that touches a high-risk (`verify: independent`), unmapped or gate path merges, one verifier from another model family posts a verdict at the current head. It reuses green CI, drives the changed journeys when users see the change, and after a fix re-checks only the changes (`--since`). A failed or blocked verdict says whether the change or a rule it was judged against is wrong (`--cause change|rules|both`): a wrong rule (stale, contradicted by a newer owner decision or another rule, or impossible for this change) still blocks the merge, and goes to the owner with a proposed adjustment instead of looping on fixes; no agent sets a rule aside on its own ([change or rules](references/verification.md#change-aware-verification-and-the-merge-gate)). Static and CI-only changes need no independent verdict, but must still be right: their checks are the evidence, and a failed verdict at the head blocks them. Keep each PR's checks proportional: run the suites the map and recorded coverage select for the changed files, split across parallel jobs, and run the whole suite only when the owner's `full_suite` choice says so and before a release ([proportional cost](references/verification.md#keep-each-pr-proportional)). When a change adds, moves or removes an area, update the map in the same PR following [guided mapping](references/mapping.md); `verify_plan.py ci` fails until every tracked file is mapped. Before driving the app, run `verify_plan.py smoke` for its target and report a failed step as a blocker instead of retrying. The `jfactory verified` status enforces this where the repository requires that check. The supplied evidence runner can record real commands and check freshness/coverage. It does not judge whether a test meaningfully proves the customer outcome. Inspect the assertions and actual result yourself.

## Implement, observe, correct

For meaningful interface changes, proactively use the [UX skill](skills/jfactory-ux/SKILL.md) to inspect the running experience and iterate against the agreed customer task. Use its reference-research mode when the user requests app research or a specific design uncertainty warrants it. When the owner asks to bug bash or hunt for bugs, use its [bug bash](skills/jfactory-ux/references/bug-bash.md): parallel explorers with one charter each, and every finding proven by a repro test that fails for the reported reason before it is reported as a bug. Competitor observations inform proposals; they do not become requirements without product alignment. A CLI/API-only change does not need browser research.

Choose the next unresolved criterion. Investigate actual code, implement the smallest coherent change, run the relevant check, inspect the result and side effects, and correct failures. Continue without waiting for “keep going.” Preserve the acceptance standard. After repeated failure without new evidence, change the investigation or identify a concrete blocker; continue independent in-scope work.

Select only relevant original methods from [pstack routing](references/pstack.md). Use focused regression tests where practical, real application journeys for user-facing changes, and independent review proportionate to the change. Investigation/review instructions may request bounded subagents when the host permits them. Larger competing implementations or unattended campaigns require the user's request.

Update affected canonical documentation with material decisions and results, using [documentation reconciliation](references/documentation.md) when guidance is stale or duplicated. Keep requirement, implementation, verification and owner acceptance separate. Preserve historical proof and mark affected old evidence stale. Avoid a new plan or status file every turn.

## Plan and coordinate larger work

Settle an open design or empirical question with a throwaway prototype before building on it. Split a large change into ordered PRs that each carry their own evidence. When the owner asks for several objectives in parallel, follow the [coordination procedure](references/coordination.md) and its `scripts/coord.py` tool: agree outcomes first, keep state in one GitHub program issue, write a complete task contract per unit, launch isolated Conductor workspaces under the model policy and concurrency limit, verify each PR at its head and merge one overlapping change at a time. Start parallel workspaces only on the owner's request or agreement. Archive the workspaces and sessions you create once their work is merged or abandoned. Choose each launch's model by [model selection](references/models.md): the task sets the tier, and the bundled usage reader's session and weekly readings for each account decide between that tier's primary and fallback.

If your task contract names a program issue, you are a worker: follow the [worker protocol](references/coordination.md#5-worker-protocol) and report through the tool.

## Deliver a pull request

Follow [PR delivery](references/delivery.md). Use a task branch or isolated checkout, commit only the requested work, push that branch and open a PR against the repository's actual base branch. The default is to enable protected auto-merge, without asking again, once every acceptance criterion passes at its required evidence scopes on the current head and required owner decisions are settled. Merging should deploy at most to staging; production releases happen only when the owner deliberately asks, and then follow the repository's recorded procedure through [production releases](references/release.md#release-when-the-owner-asks). If merging would release production, keep auto-merge off and follow [auto-merge setup](references/auto-merge.md#default-policy-verified-work-merges-itself-production-does-not). An owner-approved standing auto-merge policy needs no repeated permission. Check the gates in [auto-merge setup](references/auto-merge.md); do not bypass checks, push the base branch directly, or infer permission for unrelated releases.

Open PRs ready for human review by default, without `--draft`; use drafts only when requested or required by an applicable repository rule. Review status is separate from verification and merge readiness. If required behavior failed, is unchecked or blocked, continue feasible work, then name the missing proof prominently in the PR and handoff. Never call incomplete verification complete. Every claim in a report carries its evidence, or a label saying it is inferred or a guess. Documentation-only work needs appropriate documentation checks, not invented browser tests. Every completion message must include the concise evidence handoff in [PR delivery](references/delivery.md), including the PR URL and remote commit. A local commit or a bare "confirmed" is not a delivered, verified result.

## Improve the workflow from failures

Treat every owner correction, review comment and repeated failure as a signal to fix where it happens next, not only in this change. Use the strongest layer that fits, in this order: make the mistake impossible in the codebase (one paved path, a type, a boundary check); then static analysis (lint, compiler, a CI check); then agent instructions or a review bot; then a skill; and only last a written style rule that depends on human review. Agents extend the patterns they read, so a workaround left in place, or a comment that records one reviewer's remark as a rule, gets copied. Remove it or guard it with a check, and keep durable decisions in canonical records. Feedback on one PR applies to that PR unless the owner says it is a standing rule. See [the correction ladder](references/methodology.md#the-correction-ladder).

For substantial workflow changes or recurring agent failures, use the original eval playbook. Read what the agent actually did, not its summary; test variants on realistic isolated tasks across models with a blinded judge from another family; land a skill change only when it improves the target behavior, and cut instructions that the trials show the model does not need. Report available model/tool limits. Do not claim a syntax check proves skill effectiveness, a model score proves correctness, or an installed skill guarantees compliance.
